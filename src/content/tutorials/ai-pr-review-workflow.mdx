## 为什么用 AI 做 PR Review

AI 工具在代码审查中的价值：

- **快速初筛**：几秒钟完成初步审查
- **一致性**：每次审查标准一致
- **覆盖全面**：不会因为疲劳遗漏问题
- **减轻负担**：让人工审查聚焦高价值问题

## AI 擅长发现的问题

| 问题类型 | AI 能力 | 示例 |
|----------|---------|------|
| 安全漏洞 | 强 | SQL 注入、XSS、敏感信息泄露 |
| 代码风格 | 强 | 命名规范、格式问题 |
| 常见 Bug | 中 | 空指针、边界条件 |
| 性能问题 | 中 | 明显的性能反模式 |
| 业务逻辑 | 弱 | 需要领域知识的判断 |
| 架构设计 | 弱 | 需要全局视角的决策 |

## AI 审查 + 人工审查的分工

```
AI 审查（自动）
├── 安全扫描
├── 代码风格检查
├── 常见问题检测
└── PR 描述生成

人工审查（必须）
├── 业务逻辑正确性
├── 架构和设计决策
├── 测试覆盖充分性
└── 最终合并决策
```

## 配置建议

### PR-Agent 配置示例

```toml
# .pr_agent.toml
[pr_reviewer]
require_focused_review = true
require_tests = true
extra_instructions = """
重点关注：
- 安全问题
- 性能影响
- 错误处理
"""

[pr_description]
publish_labels = true
```

### 审查规则定制

```yaml
# 自定义审查规则
rules:
  - name: "检查敏感信息"
    pattern: "(password|secret|api_key)\\s*="
    severity: high
    message: "可能包含敏感信息，请检查"

  - name: "检查 TODO"
    pattern: "TODO|FIXME"
    severity: low
    message: "包含未完成的 TODO"
```

## 审查清单

### AI 审查后人工检查

- [ ] AI 发现的问题是否准确
- [ ] 是否有 AI 遗漏的问题
- [ ] 业务逻辑是否正确
- [ ] 测试是否充分
- [ ] 是否符合架构规范

### 常见误报处理

- 标记为误报，避免重复提醒
- 调整规则，减少噪音
- 记录误报模式，优化配置
